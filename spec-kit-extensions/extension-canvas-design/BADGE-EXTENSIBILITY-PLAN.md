# Badge input controls: implementation plan

## Baseline and compatibility boundary

The generated app already has the badge execution model: `designer-host/badges-settings/badge-types.json` defines nine type-to-rule links; `generated-host/badges/rules/*.json` declares inputs, placeholders, `placementPhaseInput`, and a generated `adapter`; `generated-host/badges/adapters/*.mjs` evaluates evidence. Preserve those links and evaluators. `generated-scaffold/badge-runtime.mjs` collects only declared outputs, directories, and runs, bounds reads and evaluation, and invokes a hash-checked evaluator in a worker. The new Designer editor must never evaluate rules or authorize additional evidence.

The missing link is rule-to-Designer-input-control registration. Currently `plugins/spec-kit-copilot-wizard/extensions/speckit-canvas-designer/ui/badges-control.js` creates inputs and has `ordered-artifacts` and `checklist-complete` branches; it also owns type selection, placement, appearance, preview, and instance actions. `external-badges.mjs` validates saved instances, `settings.mjs` checks them on load/Save, and `generation.mjs` rechecks and freezes only selected generated rule/evaluator assets. `scripts/generate.mjs` independently verifies frozen rules and writes only generated assets into the app. Do not copy Designer adapters or bindings into that app, change already-generated apps, or bump package versions during development.

## Implementation sequence

1. **Define the Designer-only registry.** Add a bounded, replace-only named template kind for a badge input-control JSON definition (stable control ID, Designer adapter template name, supported input descriptor types), a separate named rule-to-control binding (rule ID, control ID), and a self-contained `.mjs` badge-input-adapter kind. Register them in `extension.yml`, `commands/load-page.md`, `scripts/verify-launch.mjs`, and the `pages.mjs` template loader; expose resolved bindings and adapter names in the Designer model and serve their frozen bytes through `server.mjs` (as existing Designer adapters are served). A control can serve many rules; require exactly one effective binding per enabled or saved rule, one control definition per ID, and one registered adapter per referenced control. The binding belongs in `designer-host/`, not in the generated rule JSON or `canvas-config.json`. Specify still chooses whole-file winners; registration requires explicit names, not directory scanning. Reject duplicate IDs, collisions, unsupported kinds/imports, wrong exports, missing dependencies, and mismatched provenance; include the winning template name and source in diagnostics. Decide and document the JSON/adapter contract before adding the stock registration.

2. **Establish the control API and authoritative validation.** Pass `mount({root, rule, inputs, phases, outputs, onChange})` a confined root, canonical rule descriptors, structured input snapshot, and confirmed evidence choices; the adapter returns a readiness handle with optional disposal. `onChange(nextInputs)` replaces the structured inputs; the host enforces exact declared input IDs/types and does not accept control-supplied rule definitions, phase/output inventories, or privileged actions. Define update/remount behavior when badge-declared output evidence changes, disposal and failure UI, accessible focus/errors, and a predictable default-value path for new instances; do not silently repair saved instances. Match the existing text (1-256), phase, artifact, artifact-set, and ordered-artifact shapes. Reuse server-owned badge validation at load, Save, and Generate; keep generator and generated-runtime checks independent at their own boundaries. Treat browser validation as UX, never the trust boundary.

3. **Keep existing rule relationships separate from package dependencies.** `ordered-artifacts.before` already expresses its target relationship and stays on the rule. `checklist-complete` currently requires `prerequisite` to precede `artifact`, but this is encoded as a compatibility special case in validators. Preserve that behavior without expanding the rule schema in this change; review compatibility and request a separately demonstrated need before generalizing this constraint for preset rules. Input relationships are **not** package dependency edges.

4. **Move stock rendering into a registered control.** Put the five current input-type editors, labels, hints, default selection behavior, and ordered-chain explanation in a stock Designer JSON/`.mjs` package. Register the stock control for each compatible default rule; use an explicit per-rule binding, never an ID switch in `badges-control.js`. Preserve Checklist complete's two-output ordering/defaults and Phase artifact complete's target/prerequisite flow. Keep the host responsible for type picker, placement (including phase-card derivation from selected evidence or `placementPhaseInput`), legacy targets, per-placement text/placeholders, color, preview, duplicate detection, Save/Create, and Remove. Move only input-derived UI and validation out; ensure the host recomputes phase placement when the adapter changes inputs. Preserve default type ordering, labels, text, colors, zero initial instances, and all current placements.

5. **Make composition changes diagnosable before adoption.** Keep the existing single whole-file `badges-settings` type list: a preset replaces it to add/rename/disable/remove types, and independently adds or replaces named rules, evaluators, control definitions, adapters, and rule bindings. Define effective-state checks for each change: type -> rule -> generated evaluator and rule -> Designer binding -> control -> adapter; report the saved badge IDs and dependent type/rule/control/evaluator template names affected by a replacement or omission. A disabled type stays identifiable but cannot be added or edited until repaired; a missing rule, binding, control, or evaluator is a different actionable error, never a stock-editor or alternate-evaluator fallback. A rule replacement that changes input IDs/types or evaluator contract requires explicit repair of affected instances. A control removal is blocked while effective bindings or saved instances depend on it; unused removals may proceed. Preserve saved bytes and block invalid Save/Generate; report the affected IDs and dependencies so the preset can be restored or the badges edited/removed through existing actions. **Do not build automatic conversion or a separate recovery UI.**

6. **Carry checks across boundaries.** At Designer load, validate the entire registered graph and show actionable composition errors while retaining healthy pages where possible; distinguish a disabled catalog type from a missing capability. At Save, independently validate every persisted instance's effective type/rule/control/evaluator, exact inputs, declared relationships, outputs, text, color, placements, and duplicate constraints. At Generate, re-resolve the frozen winning templates, revalidate saved instances and adapter readiness, freeze only selected types/rules/evaluators and hash-check their bytes; extend `scripts/generate.mjs` verification where rule constraints change, not to package Designer code. Keep the generated app's own startup input/adapter checks and safe-evidence collection as the final runtime boundary. Diagnose unavailable generated badge destinations through the existing Workflow/phase adapter capability checks.

## Acceptance fixtures and checks

- Add a **test-only** `canvas-design` preset fixture, registered through the composed `load-page` command and Specify template inventory, with a new type, rule, generated evaluator, custom Designer control definition/binding, and a visibly different explanatory layout/adapter. Do not edit `badges-control.js` to recognize its ID. Verify keyboard-accessible editing, changed outputs, draft validation, Save/reopen with exact inputs, Generate, copying/opening the packaged app without the design preset, positive/negative runtime matching, and undeclared-evidence denial.
- Test add and whole-file replacement, disable, missing/removed type, rule, binding, control and evaluator, reused controls, incompatible input signatures, collisions, stale saved model revisions, affected-instance/dependent-component diagnostics, and no fallback editor/evaluator. Test `before` separately from package dependency removal.
- Run the existing targeted suites in `plugins/spec-kit-copilot-wizard/extensions/speckit-canvas-designer/test/{badges-control,badges,provider}.test.mjs` and `spec-kit-extensions/tests/{badge_adapters,generated_badges,generated_badge_placements,ordered_badge_generation}.test.mjs`; extend `scripts/verify-launch.mjs` registration tests and generator frozen-request tests. Compare stock badge defaults, labels, saved JSON, placements, evaluation, and generated output against the current baseline. Update this extension's README and relevant schemas/contracts when the implementation lands. Worktree/local-source success is not evidence that the catalog-selected published archive supports the hosted path; verify that archive separately before declaring a release ready.
