# Implementing the Wizard → Designer user-flow test plan

## Problem and approach

The original test suite had strong lower-level contracts and substantial Designer/generated-canvas browser coverage, but little browser coverage of the Wizard's setup, catalog, composition refresh, pipeline, phase run, and output journeys. Some browser tests asserted invented catalog copy/counts, duplicated lower-level checks, or used wall-clock timings. The [flow plan](wizard-designer-test-plan.md) was implemented in stages: first create package-backed deterministic fixtures and harnesses; then add the missing browser journeys; finally consolidate tests only when replacement coverage passes. Keep distinct security, provenance, and data-loss regressions, however rare their inputs. Include the generated canvas.

The plan was approved and locally implemented. The validation results below were recorded after integrating newer `main` changes. Verification against the published catalog-selected archive remains a separate release-readiness check.

## Required testing contract

- Routine Playwright runs use a real loopback Wizard/Designer/generated server, a fresh temporary project per scenario, seeded **controlled** catalog data, and a fake `session.send` that records prompts without running a live agent. Deliver responses through the real `showInferredPipeline` action, phase actions, and artifact-targets endpoint. Do not mock the DOM or final snapshots for the cross-boundary journey.
- A live catalog is discovery data: assert tabs, source categories, search/filter behavior relative to the current snapshot, selection/retry, and no invented installed state. Never assert a complete list, fixed count, current version, ordering, descriptive copy, or uncontrolled bundle membership. For package-specific checks use local fixtures or team-owned, verified built-ins. Pirate Speak is team-controlled Community data: catalog ID `pirate`, installed ID `pirate-full-preset`; fetch other fields from the fixture snapshot. Do not conditionally skip a required PR test if the live catalog changes.
- **No arbitrary version pins in tests.** Derive preset/extension/plugin versions from source manifests, selected entry metadata from the catalog snapshot, and CLI compatibility samples from the production minimum-version rule. Assert propagation, equality to the installed manifest, or behavior immediately on either side of a supported boundary; never assert that the product currently displays a particular release number. Only retain a literal version in a focused, documented regression that specifically protects a stable compatibility floor or parser boundary, not in a browser journey. Do not approve volatile release labels in snapshots.
- Separate local-source PR testing from hosted release readiness. A hosted test must inspect the archive selected by the published catalog, not worktree source. No development-driven version bump, tag, or publication.
- Use accessible locators and web-first assertions; assert intermediate states through explicit deferred promises (no sleeps). Do not require a refresh spinner in individual phase cards: the current UI indicates it in Composition and the Phases banner.
- Node tests own parsing, schema/normalization, malformed inputs, fingerprints, filesystem boundaries, provenance and version permutations; browser tests own interaction, focus, intermediate state, actual SSE/HTTP navigation, and one representative packaged result.

## Work packages and dependencies

1. **Baseline and coverage map.** Record commands and baseline results for existing Wizard Node, Designer Node, Playwright, and generator checks; map test names to W1–W24, D1–D26, G1–G3 in the flow plan. For every proposed deletion document the replacement assertion and the actual code path exercised. Preserve dirty worktree edits; no blanket test-file rewrites.
2. **Controlled package fixtures.** Keep `copilot-wizard-layer-test` alongside the other test-only presets in `tests/fixtures/test-presets/`, outside the shipping `spec-kit-presets/` directory and catalog. Its `preset.yml` and real command files provide a `replace` for `speckit.plan` and `prepend` for `speckit.specify`, with distinguishable source evidence; the prepend forces Stage 2. Keep `extension-wizard-flow-test` separately in `tests/fixtures/specify/`, not the publishable `spec-kit-extensions/` scan or catalog. Its `extension.yml`, README, real files, skill and hook registration provide the namespaced runnable `speckit.extension-wizard-flow-test.review` with a primary and secondary Markdown output and README ordering signal, plus an `after_plan` hook command that appears as a hook but never as a pipeline step. Reuse existing `copilot-sub-agents` and Canvas Design test presets rather than duplicating them. Create temporary mutated copies for negative cases. Add structural/install-resolution checks that prove manifests reference real files and installed package IDs/versions/skill metadata align; read versions from the manifests rather than duplicating them in assertions. Run a real `specify preset add --dev` smoke for every test preset where the CLI is part of the configured CI job, never silently treat a missing CLI as a pass.
3. **Deterministic harness.** Extend the fixed data in `tests/e2e/server.mjs` only for controlled dialog scenarios; add a small per-test temporary Wizard server/instance fixture for dynamic composition, SSE and agent callback tests (using existing `startServer`/runtime helpers rather than a second simulation). Expose deferred skills reload, fake agent prompt capture, fixture-owned catalog inventory, current fingerprinted inference requests, controlled bundle-member responses, and guaranteed cleanup. Keep independent browser contexts/tests and filesystem state isolated. Avoid a global one-server shared mutable snapshot for these journeys.
4. **Wizard browser journeys.** Add `tests/e2e/wizard-journeys.spec.mjs` (split only if it grows unwieldy): W1/W4 setup ready and recovery; W7–W12 controlled catalog selection, Composition layer/hook and removal; W13–W15 click Refresh, hold the fake turn, assert Composition/Phases pending state, deliver pipeline and outputs separately, assert final artifact/stepper/card and retry/fast path; W16–W18 edit/reset/navigation; W19–W24 run/receive report, pending retry, verified output/viewer. Assert only controlled fixture IDs/paths. Add focused Node tests for anything missing in validation; do not clone the browser journey as a series of HTML-string tests.
5. **Designer/handoff and generated journeys.** Adapt `tests/e2e/canvas-designer.spec.mjs`, `contracts.spec.mjs`, `designer-essentials.spec.mjs`, `designer-pages.spec.mjs`, and `generated-slug.spec.mjs` to anchor package-specific assertions to built-in/controlled fixtures. Keep representative real Specify install/resolve journeys for an added page, paired risk control, and portable generated result. Preserve Save/reopen, Outputs, upload/error, approval, stale revisions, custom slug, generated state recovery, adapter failure, accessibility, and CSP browser coverage. Avoid the combinatorial cross-product of test presets. Add browser gaps only where a real user boundary is untested; keep lower-level validation exhaustive.
6. **Consolidate/remove after replacements.** Apply the audit matrix below only once the corresponding work-package tests pass. Keep any test whose apparently overlapping assertion proves a different boundary. Do not remove a unique regression for integrity, race isolation, path confinement, or accessibility merely to reduce counts. Use one representative browser failure and the lower-level matrix for the rest.
7. **Validation and handoff.** Run targeted Wizard Node tests, Designer Node tests, and only changed Playwright specs first. Escalate to the full `npm run test:e2e` and generator/extension validation once changed specs pass. Run affected tests in a clean, isolated workspace and rerun the new deferred-response journeys to check for timing/flakiness. Record resulting W/D/G coverage, purposeful gaps, and the separate hosted archive release-readiness status. No release publication.

Dependencies: package fixtures precede the harness's installation paths and Wizard journeys; harness precedes new cross-boundary browser tests; new/updated coverage precedes removals; validation follows each stage and final consolidation. The baseline and contract-only Node checks can proceed independently of fixture creation.

## Decisions and acceptance criteria

- No test is removed merely because its scenario is rare. Each removal needs (a) equivalent assertion against the production path in a cheaper or combined test, (b) passing replacement, and (c) a diff proving no unique boundary was lost. If uncertain, retain the test and flag for later review.
- The existing `tests/e2e/server.mjs` has static synthetic names such as “Design preset” and “Community bundle”; they are controlled *test data*, but their complete displayed list/copy must not become a product contract. Identify package entries by fixture-owned ID, derive optional item details from the served snapshot, and assert an item’s transition rather than total cards.
- If an assertion uses a version literal, annotate the precise compatibility guarantee it protects and review it when the production floor changes; otherwise obtain the expected value from the current manifest/catalog. For hosted verification, use the release archive selected by the published catalog and compare the extracted manifest/installed result, not a remembered ZIP version.
- Keep the new fixture extension out of workflows that auto-package all `spec-kit-extensions/extension-*` directories. Test-only presets remain outside `spec-kit-presets/catalog.json`. Do not mutate globally installed plugin providers or the main checkout to run unit/browser tests.
- The Wizard/Designer source has pre-existing uncommitted changes; plan applies on top of them and does not revert or overwrite unrelated edits. Re-read touched files immediately before implementation.
- Targeted and full validation must pass; browser tests must report a real intermediate UI transition and final state, not merely that a prompt was sent or an API returned 202. Hosted release-readiness remains separately labeled until the published archive has been verified.

## Execution record and final test dispositions

The controlled preset and extension packages were added outside production catalogs, and their installed manifests, layers, hook, and Specify CLI resolution were checked. Eleven temporary-checkout Wizard browser journeys now cover boot recovery, environment/skills retry, catalog and controlled-bundle transitions, layer navigation, two-part Refresh and retry, pipeline editing during Refresh, phase status/report and retry, and real artifact viewing. Designer browser coverage includes controlled local/hosted selection and handoff, contributed fields, Outputs, uploads, save/reopen/conflicts, the built-in light/dark palette and invalid-color feedback, and real Specify-to-generated package journeys. Generated-canvas browser coverage retains adapter, workflow, draft, phase and viewer behavior.

| Disposition | Applied decision and protected boundary |
|---|---|
| **Keep** | Provider/contract and browser security, provenance, path-confinement, stale-revision, data-loss, accessibility, CSP, and race regressions; the real package-resolution and generated-runtime journeys. They protect boundaries that a happy-path Refresh test cannot replace. |
| **Change** | Browser expectations for catalog inventory and selected releases now use controlled fixture IDs or the current response/manifest rather than arbitrary live names, totals, order or release versions. Controlled Composition and Designer paths are exercised through real servers and fake deferred agent turns. Real bundle manifest structure was validated with `specify bundle validate --offline`. |
| **Consolidate** | The new Wizard journeys share per-test checkout/server setup and combine pending, pipeline, output and run assertions instead of repeating browser setups. Existing Designer dialog/Essentials assertions were narrowed and their queued/approval transitions strengthened; the palette scenario extends the existing real-package journey rather than spawning another costly install test. |
| **Remove after replacement** | Deleted the browser-only test-local version parser (production minimum-version tests remain), the quoted-local-path browser duplicate (real local-source canonicalization stays in Node), and the browser-less failed-shell assertion (the provider test now exercises the rejection). |
| **Retain rather than move prematurely** | The 21st-local-item browser case and generated adapter error variants remain until an equivalent production UI-controller/packaged-loader seam exists. Distinct failure diagnostics and the intended 20-item threshold must not be lost for a cosmetic test-count reduction. |

Final local validation after integrating newer `main` changes: Wizard Node **424 passed, 1 skipped**; Designer Node **55 passed, 2 skipped**; generated-canvas Node **159 passed**; extension Python package checks **17 passed, 1 skipped**; complete Playwright **80 passed**. Deferred Wizard journeys also passed repeated isolated runs. No release/package/catalog versions were bumped. D9 is intentionally **release-only and unverified**: local worktree/source tests do not establish hosted readiness until the published archive selected by the catalog is checked. G1 was covered by a real Specify preset-to-served-generated-canvas journey plus generated-runtime interactions. The subsequent [test-preset E2E strategy](../../tests/e2e/README.md) adds Wizard-handoff-to-Designer and generated-canvas browser journeys for every test-only preset through its last affected surface; the published archive still requires separate release verification.
